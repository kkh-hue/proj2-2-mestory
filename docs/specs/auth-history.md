# 로그인과 분석 히스토리 준비

## Why

- **페르소나**: 이전 설비 분석 결과를 다시 확인하려는 현장 관리자
- **상황**: 현재 분석 결과는 브라우저 화면과 일시적인 세션 안에서만 확인한다.
- **문제**: 사용자 계정과 분석 결과를 연결해 보관하거나 다시 조회할 구조가 없다.
- **측정 지표**: 인증·저장 API가 준비된 뒤 기존 분석 화면을 최소 연결로 로그인과 사용자별 히스토리에 연결할 수 있다.

## Goal

- 로그인 폼과 분석 히스토리의 독립 UI·타입 계약을 준비한다.
- 히스토리 항목이 분석 일시, 조회 기간, 라인, 설비 및 원본 `DowntimeReport`를 보관할 수 있게 정의한다.
- **Out of Scope**: 실제 인증, 비밀번호 전송·저장, JWT 발급, DB migration, Railway 설정, 기존 화면 연결, 가짜 사용자·히스토리 데이터.

## What

**Happy Path**

1. `LoginForm`은 향후 인증 핸들러에 이메일과 비밀번호를 전달할 수 있다.
2. 인증 핸들러가 없는 현재는 로그인 불가 상태와 안내만 표시한다.
3. `AnalysisHistory`는 사용자별 히스토리 항목을 받아 목록을 표시한다.
4. 선택 콜백은 저장된 항목의 원본 `DowntimeReport`를 전달해 향후 결과 화면에서 재표시할 수 있다.

**Edge Cases**

| 상황 | 처리 |
| --- | --- |
| 인증 API 미연결 | 로그인 성공을 가정하지 않고 비활성화 안내를 표시한다. |
| 히스토리 없음 | 가짜 데이터를 넣지 않고 빈 상태를 표시한다. |
| 로그인 실패 | 향후 핸들러가 반환한 오류만 표시한다. |
| 선택된 항목 없음 | 결과 재표시 콜백을 호출하지 않는다. |

## How

- `session_id`는 현재 LLM 대화 문맥/trace 용도이며 `user_id`와 별개의 값이다.
- 향후 저장 단위: `analysis_id`, `user_id`, `created_at`, 조회 조건, `DowntimeReport` 스냅샷.
- 개인정보 원칙: 비밀번호 평문 저장 금지, 프론트에서 JWT 생성 금지, 실제 인증 방식(OAuth·세션·외부 IdP)은 팀 합의 후 결정한다.
- 현 Postgres는 MCP 데이터 원본 조회에 사용되므로 인증·히스토리 테이블과 권한 설계는 별도 migration으로 결정한다.
- 신규 파일만 추가하며 기존 API, DB, 화면에는 연결하지 않는다.

## AC (Given-When-Then)

- GIVEN 인증 핸들러가 없을 때, WHEN 로그인 폼을 렌더링하면, THEN 로그인 성공 처리나 임의 사용자 생성 없이 미연결 상태가 표시된다.
- GIVEN 빈 히스토리 배열일 때, WHEN 히스토리를 렌더링하면, THEN 가짜 분석 항목 없이 빈 상태가 표시된다.
- GIVEN 저장된 히스토리 항목이 있을 때, WHEN 사용자가 항목을 선택하면, THEN 해당 항목의 원본 `DowntimeReport`가 선택 콜백으로 전달된다.
- GIVEN 현재 `/report` 요청의 `session_id`가 있을 때, WHEN 히스토리 모델을 사용해도, THEN 이를 `user_id`로 사용하지 않는다.
