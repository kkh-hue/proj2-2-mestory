## 1. 배경 및 문제 정의

### 1-1. 배경

팀원 홍민하는 2년간 MES 솔루션을 풀스택 개발자로 개발·유지보수하며 정지이력·리포트/대시보드·품질/작업지시 모듈을 직접 다뤘다. 이 과정에서 고객사(현장) 담당자로부터 "왜 이 라인이 이만큼 멈췄는지" 원인 분석을 요청받는 일이 반복적으로 발생했고, 그때마다 담당자가 정지 로그를 수작업으로 뒤져 설명 자료를 만들어야 했다. 시스템 안에 원인 분석을 표준화해서 제공하는 기능이 없다는 점이 이번 프로젝트의 출발점이다.

### 1-2. 문제 정의

설비 정지(다운타임) 로그가 쌓여도, 원인을 사람이 매일 수작업으로 분류·집계하여 보고서를 작성하고 있다. 이 작업은 반복적이고 시간이 걸리며, 담당자의 경험치에 따라 결과 품질이 달라진다.

### 1-3. 왜 지금, 왜 LLM인가

- 정지 로그·에러코드 사전·정비이력은 이미 정형 데이터로 MES 안에 쌓여 있음 — 데이터 확보 비용이 낮음.
- 기존 MES 대시보드는 집계·시각화까지는 하지만, "왜 발생했는지 자연어로 설명"하고 "근거를 근거 데이터에 연결"하는 부분은 비어 있음 — 이 빈틈이 LLM이 개입할 지점.
- 정답이 있는 케이스(정상/실패유도)는 규칙 기반 자동화로도 처리 가능하지만, 여러 원인이 겹치거나 애매한 케이스는 사람이 근거를 참고해 판단하도록 돕는 것이 서비스의 핵심 가치.

## 2. 목표 및 성공 지표

### 2-1. 제품 목표

- 설비 정지 로그 + 에러코드 사전 + 정비이력을 근거로, 원인·심각도·권장 조치가 포함된 구조화된 리포트를 자동 생성한다.
- 정답이 명확한 케이스는 스키마 준수율 높은 안정적 자동 응답을, 애매한 케이스는 '판정 불가/확인 필요'를 정직하게 표시해 사람의 최종 판단을 돕는다.
- 모든 응답은 Langfuse로 추적되어, 실패 케이스와 게이트 위반을 팀이 상시 관찰할 수 있다.

### 2-2. 성공 지표 (KPI / 게이트)

| 구분 | 지표 | 목표치 | 비고 |
|---|---|---|---|
| 품질 게이트 | Pydantic 출력 스키마 준수율 | ≥ 95% (100회 이상 실행 기준) | 미달 시 서비스 배포 불가 조건 |
| 품질 게이트 | 미등록 에러코드 환각(hallucination) 발생률 | 0건 | 정답 대신 '확인 필요' 응답 강제 |
| 성능 | 리포트 생성 p95 응답시간 | 추후 측정 후 확정 (초안 목표 10초 이내) | MCP 조회 + LLM 호출 포함 총 시간 |
| 평가 | 평가셋 정답률 (정상/실패유도, 코드 검증 가능 케이스) | ≥ 90% | 경계 케이스는 별도 트랙으로 채점(정답 미확정) |
| 관측 | Langfuse 트레이스 커버리지 | 100% (모든 호출 기록) | input/output/지연시간/토큰 포함 |

> ※ 경계(4문항) 질문은 팀 내 현장 경험 부재로 확정 정답이 없으므로, 정량적 '정답률' 대신 '근거 제시 여부'와 '판정 불가를 정직하게 표시하는지'를 채점 기준으로 별도 관리한다 (proj2-2_계획보완.docx 참고).

## 3. 대상 사용자 및 사용 시나리오

### 3-1. 대상 사용자

| 사용자 | 니즈 | 현재 방식 |
|---|---|---|
| 생산관리자 / 설비 엔지니어 | 라인이 왜, 얼마나 멈췄는지 빠르게 파악하고 조치 우선순위를 정하고 싶음 | 정지 로그를 엑셀로 내려받아 수작업 집계 |
| 고객사(현장) 담당자 | 정지 원인에 대한 설명 자료를 요청받았을 때 신속히 받고 싶음 | 개발팀·현장 담당자가 매번 수작업으로 자료 작성 |

### 3-2. 핵심 사용 시나리오 (User Flow)

1. 사용자가 조회할 기간/라인/설비를 지정해 리포트 생성을 요청한다 (챗봇형 UI).
2. 에이전트(LangChain + MCP)가 해당 기간의 정지 로그를 조회하고, 에러코드 사전·정비이력을 MCP 도구로 추가 조회한다.
3. LLM이 조회된 데이터를 근거로 원인·심각도·권장 조치를 Pydantic 스키마에 맞춰 구조화된 리포트로 생성한다.
4. 미등록 코드·데이터 오류·판단 근거 부족 케이스는 '확인 필요'로 명시하고, 사람이 최종 확정한다(HITL).
5. 모든 요청/응답은 Langfuse에 트레이스로 기록되어 이후 평가·개선에 사용된다.

## 4. 범위 (Scope)

| 구분 | 내용 |
|---|---|
| 한다 (In Scope) | 정지 로그를 원인별로 자동 집계하고, 심각도·권장 조치까지 구조화된 리포트로 생성한다. 에러코드/정비이력 기반 근거 제시, 미등록 코드·데이터 오류 케이스의 실패 안전 처리(fail-safe). |
| 하지 않는다 (Out of Scope) | 실시간 설비 제어나 자동 조치 실행은 하지 않는다. 최종 원인 판단과 조치 실행은 사람이 한다(HITL). 여러 라인을 동시에 스케줄링하는 기능은 범위 밖. RAG(청크 검색 기반 문서 응답)는 사용하지 않는다. |
| LLM이 맡는 일 | 에러코드+정비이력을 근거로 한 자연어 설명 생성, 복수 원인 중 우선순위 판단 근거 제시(단, 확정 아님을 명시), 표준 권장 조치 문구 매칭. 최종 확정은 사람의 몫임을 모든 출력에 명시. |

## 5. 기능 요구사항

### 5-1. 핵심 기능 목록

| ID | 기능 | 설명 | 우선순위 |
|---|---|---|---|
| F-01 | 정지 로그 조회 (MCP) | 기간/라인/설비 조건으로 downtime_log 조회하는 MCP 도구 | P0 |
| F-02 | 에러코드 사전 조회 (MCP) | error_code_dict에서 코드별 typical_duration, severity_hint 조회. 미등록 코드는 명시적 '없음' 반환 | P0 |
| F-03 | 정비이력 조회 (MCP) | equipment_id 기준 최근 정비이력 조회 — 근본원인 추정의 근거로 사용 | P0 |
| F-04 | 원인 분석 리포트 생성 | LangChain 도구 호출 에이전트가 F-01~03 결과를 근거로 Pydantic 스키마(DowntimeReport) 리포트 생성 | P0 |
| F-05 | 실패 안전 처리 | 미등록 코드/음수 정지시간/빈 필드 등은 원인 추정 없이 '확인 필요'로 응답 | P0 |
| F-06 | 복수 원인 우선순위 표시 | 동시 발생 케이스는 잠정 우선순위 + 판단 불확실성을 함께 표기 | P1 |
| F-07 | 챗봇형 대화 UI | Streamlit 또는 React(Next.js) 기반, 조회 조건 입력 후 리포트를 대화형으로 표시 | P0 |
| F-08 | Langfuse 트레이스 연동 | 모든 요청의 입력/출력/지연/토큰을 기록, 대시보드에서 게이트 위반 확인 | P0 |
| F-09 | 평가셋 자동 채점 스크립트 | 30건 이상 평가셋에 대해 스키마 준수율/정답률을 자동 계산 | P1 |

### 5-2. 출력 계약 (Output Contract)

모든 응답은 Pydantic 모델(DowntimeReport, DowntimeCause)로 구조화되며, 3단계 재시도/폴백 전략을 적용한다: ① 1차 생성 실패 시 프롬프트 재시도, ② 2차 실패 시 스키마를 단순화한 축소 버전으로 재시도, ③ 모두 실패 시 "자동 분석 실패 — 원본 로그 확인 필요"라는 고정 안전 응답을 반환한다.

| 필드 | 타입 | 설명 |
|---|---|---|
| equipment_id / line_id | string | 대상 설비/라인 식별자 |
| period | string | 분석 대상 기간 |
| causes | List[DowntimeCause] | 원인 목록 (코드, 설명, 심각도, 근거, 확실성 여부) |
| unclassified_count | int | 미등록 코드·데이터 오류 등 판정 불가 건수 |
| confidence_note | string | 경계 케이스일 경우 판단 불확실성과 사람 확인 필요 여부 명시 |
| recommended_action | string | 표준 권장 조치 문구 (정비팀/자재팀 등 담당 구분 포함) |

## 6. 비기능 요구사항

- **신뢰성**: 스키마 검증 실패율 5% 이하, 모든 실패는 안전한 폴백 응답으로 종료(예외로 서비스 다운되지 않음).
- **정직성/투명성**: 근거 없는 원인 단정 금지(hallucination 금지) — 미등록 코드·데이터 오류·경계 케이스는 반드시 불확실성을 명시.
- **관측 가능성**: 모든 호출은 Langfuse에 트레이스로 남고, 게이트 위반(스키마 실패, 환각 등)은 즉시 식별 가능해야 함.
- **이식성**: FastAPI + Docker/docker-compose로 패키징해 로컬/서버 환경에서 동일하게 재현 가능해야 함.
- **보안/데이터**: 이번 프로젝트는 시뮬레이션/공개 데이터셋만 사용하며 실제 고객사 데이터는 사용하지 않는다.

## 7. 시스템 아키텍처 개요

- **LLM**: OpenRouter 경유 모델 호출
- **에이전트 프레임워크**: LangChain (`create_tool_calling_agent` + `AgentExecutor`) — LangGraph 미사용, 단발성 도구 호출형 에이전트
- **도구 연동**: MCP 서버(`mcp.server.fastmcp.FastMCP`)로 정지 로그/에러코드 사전/정비이력 조회 도구 제공 → `langchain_mcp_adapters.tools.load_mcp_tools`로 LangChain에 연결
- **지식 문서**: Skill 문서(SKILL.md, 정적 전체 문서 제공 — RAG 아님)로 판정 규칙·금지사항(임의 원인 추정 금지 등) 명시
- **백엔드**: FastAPI, 출력 계약은 Pydantic으로 강제
- **관측/평가**: Langfuse로 트레이싱, 평가셋 스크립트로 정기 채점
- **배포**: Docker 또는 GCP(구글 클라우드)
- **프론트엔드**: Streamlit 또는 React(Next.js) 기반 챗봇형 UI

## 8. 평가 계획

평가셋은 정상/경계/실패유도 3가지 유형으로 구성하며, 현재 10건(초안) → 30건 이상으로 확장 예정이다. 정상·실패유도 케이스는 코드/스키마 규칙으로 정답이 확정되어 자동 채점이 가능하지만, 경계 케이스는 팀 내 현장 경험 부재로 확정 정답이 없어 "판단 근거 제시 여부"를 기준으로 별도 채점한다 (proj2-2_계획보완.docx, 평가셋_10건_초안.xlsx 참고).

| 유형 | 건수(초안) | 채점 방식 |
|---|---|---|
| 정상 | 3건 | 에러코드 사전의 typical range/severity_hint와 자동 비교 |
| 경계 | 4건 | 정답 미확정 — 근거 제시 여부·불확실성 명시 여부로 정성 채점, 착수 세션에서 현장 전문가 자문 예정 |
| 실패 유도 | 3건 | 미등록 코드/음수 값/빈 필드에 대해 '확인 필요' 응답 여부를 자동 검증 |

> 평가셋 정답 판정은 특정 1인이 아닌 3인 전원 합의로 결정하며, 현장 경험이 필요한 경계 케이스는 착수 세션에서 강사님 및 도메인 전문가 자문을 통해 범위를 조정한다.

## 11. 리스크 및 완화 계획

| 리스크 | 완화 계획 |
|---|---|
| 팀 전원 현장 진단 경험 부재 → 경계 케이스 정답 신뢰도 낮음 | 경계 케이스는 정답 확정 대신 '판단 근거 제시'를 평가 기준으로 전환. 착수 세션에서 도메인 전문가 자문 또는 해당 문제를 서비스 범위에서 제외하는 방향 논의 |
| 시뮬레이션 데이터가 실제 현장 패턴과 다를 수 있음 | 공개 Kaggle 제조/설비 데이터셋을 보조 자료로 병행 검토, 평가셋에 현실적인 이상치(미등록 코드, 데이터 오류) 포함 |
| LLM이 근거 없이 원인을 단정(hallucination)할 위험 | Skill 문서에 '임의 추정 금지' 명시, 실패유도 평가 케이스로 상시 검증, 미등록 코드는 스키마 단계에서 강제 차단 |
| 일정 지연 (3인 팀, 4주 개발) | P0 기능(F-01~05, F-07, F-08) 우선 구현 후 P1은 여유 있을 때 추가 |
